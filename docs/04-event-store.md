# 04 — Event Store (MySQL 8)

## 1. Server configuration (needed by Debezium)

`binlog_format=ROW`, `binlog_row_image=FULL`, `gtid_mode=ON`, `enforce_gtid_consistency=ON`, unique `server_id`, `binlog_expire_logs_seconds` ≥ 3 days. Default isolation is `REPEATABLE READ`. `innodb_autoinc_lock_mode=2` is the default in MySQL 8.

## 2. Schema

```sql
CREATE TABLE event_store (
  global_position   BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  event_id          CHAR(36)         NOT NULL,           -- UUIDv7, generated by the app
  aggregate_type    VARCHAR(64)      NOT NULL,           -- 'VehicleInventory'
  aggregate_id      CHAR(36)         NOT NULL,
  aggregate_version INT UNSIGNED     NOT NULL,           -- 1..n, contiguous per aggregate
  event_type        VARCHAR(100)     NOT NULL,           -- 'VehicleStocked', ...
  schema_version    SMALLINT UNSIGNED NOT NULL,
  payload           JSON             NOT NULL,
  metadata          JSON             NOT NULL,
  occurred_at       DATETIME(6)      NOT NULL,           -- UTC, from the injected clock
  recorded_at       DATETIME(6)      NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (global_position),
  UNIQUE KEY uq_event_id (event_id),
  UNIQUE KEY uq_stream_version (aggregate_id, aggregate_version),   -- OCC
  CONSTRAINT ck_version_positive CHECK (aggregate_version >= 1)
) ENGINE=InnoDB;

-- Set-based constraint: one IN_STOCK vehicle per VIN (see §5). Mutable, but only written
-- inside the same tx as the events that justify it, and fully rebuildable from events.
CREATE TABLE vin_reservation (
  vin         CHAR(17) NOT NULL PRIMARY KEY,
  vehicle_id  CHAR(36) NOT NULL,
  reserved_at DATETIME(6) NOT NULL
) ENGINE=InnoDB;

-- HTTP Idempotency-Key replay store (additional feature).
CREATE TABLE idempotency_key (
  actor_id            VARCHAR(64)  NOT NULL,
  idempotency_key     VARCHAR(128) NOT NULL,
  request_fingerprint CHAR(64)     NOT NULL,     -- sha256(method, route, body)
  aggregate_id        CHAR(36)     NOT NULL,
  response_status     SMALLINT     NOT NULL,
  response_body       JSON         NOT NULL,
  created_at          DATETIME(6)  NOT NULL,
  PRIMARY KEY (actor_id, idempotency_key)
) ENGINE=InnoDB;

CREATE TABLE dealership (            -- reference data, seeded by migration
  dealership_id VARCHAR(64) PRIMARY KEY,
  name          VARCHAR(200) NOT NULL,
  timezone      VARCHAR(64)  NOT NULL   -- IANA name
) ENGINE=InnoDB;
```

Column notes:
- `global_position` provides total order for rebuild batching and serves as the Debezium PK. It is **not** used for correctness (per-aggregate version is).
- IDs are `CHAR(36)`, not `BINARY(16)`. This keeps Debezium output human-readable and avoids base64 decoding (02 R3). The storage cost is irrelevant at this scale.
- No secondary index on `aggregate_id` alone. `uq_stream_version` serves `WHERE aggregate_id=? ORDER BY aggregate_version`.

**Append-only enforcement** (defence in depth):
1. Grants: the app user `inventory_app` has `SELECT, INSERT` on `event_store`, with no `UPDATE` or `DELETE`. The projector user `inventory_reader` has `SELECT` only. The `debezium` user has `SELECT, RELOAD, SHOW DATABASES, REPLICATION SLAVE, REPLICATION CLIENT`.
2. `BEFORE UPDATE` and `BEFORE DELETE` triggers on `event_store` that `SIGNAL SQLSTATE '45000'`. These also protect against an operator mistake made as root.

## 3. Write path (one command)

```
load:    SELECT ... FROM event_store WHERE aggregate_id=? ORDER BY aggregate_version     -- no lock
         rehydrate Vehicle (fail on version gap)
check:   if expected_version given && != vehicle.Version → ErrVersionMismatch (HTTP 412)
decide:  events := vehicle.Handle(cmd, businessDate)      -- pure; may be zero events (no-op)
append:  BEGIN
           [idempotency] INSERT idempotency_key ...       -- PK clash ⇒ concurrent duplicate
           [stock]       INSERT vin_reservation ...       -- PK clash ⇒ ErrVINAlreadyInStock
           INSERT event_store (v+1), (v+2) ...            -- multi-row INSERT, one statement
           [sell]        DELETE FROM vin_reservation WHERE vin=? AND vehicle_id=?
         COMMIT
```

- **Atomic multi-event append**: all events of one command go in one multi-row `INSERT` inside one transaction. Either all versions become visible (and reach the binlog) or none do.
- **Optimistic concurrency** is enforced by `uq_stream_version` alone. Two writers that both loaded version 3 both try to insert version 4. InnoDB lets one through. The other blocks on the unique-key lock and then fails with **1062 duplicate key**, which maps to `ErrConcurrencyConflict`. No `SELECT … FOR UPDATE` and no version row.
- **Deadlock (1213) / lock-wait timeout (1205)** can happen with concurrent inserts on the same unique key. They map to `ErrConcurrencyConflict` too (retryable).

## 4. Concurrency, retries, duplicates

| Scenario | Behaviour |
|---|---|
| Two managers propose concurrently, no `If-Match` | Both load v3. One appends v4. The loser gets a conflict, and the handler **re-runs load → decide → append** (max 3 attempts, jittered backoff). On re-decide it sees the active action and returns `409 ACTION_ALREADY_ACTIVE`. The domain rule decides the outcome, never "last writer wins". |
| Two revisions concurrently, no `If-Match` | Both are valid after retry, so both are applied in order and both are in the history. This is acceptable for automation clients. |
| Two revisions concurrently **with** `If-Match: "3"` | The loser gets `412 PRECONDITION_FAILED` without retry, because the caller asserted the state they saw. This is the recommended mode for the UI. |
| Client times out, request actually committed, client retries **with the same `Idempotency-Key`** | The lookup finds the stored row. If the fingerprint matches, the server returns the stored status and body with `Idempotent-Replayed: true`. If it differs, it returns `422 IDEMPOTENCY_KEY_REUSED`. |
| Same, two retries arrive concurrently | Both miss the lookup. Both try to `INSERT idempotency_key` in their append tx. One fails with 1062 on that PK, its whole tx (including its events) rolls back, and it then returns the stored response. **Duplicates cannot produce duplicate events.** |
| Retry **without** a key | It is caught by the domain: proposing again → `ACTION_ALREADY_ACTIVE`, stocking the same VIN → `VIN_ALREADY_IN_STOCK`, selling again → `VEHICLE_ALREADY_SOLD`, revising with the same values → no-op `200`. Cancel again → `409 ACTION_NOT_ACTIVE` (documented: use an idempotency key for exactly-once semantics). |
| `StockVehicle` retried with the same client-supplied `vehicle_id` | The stream exists, so the result is `409 VEHICLE_ALREADY_EXISTS` (or a replay if a key is present). |
| MySQL unavailable | `503`, with the error logged and a metric emitted. No partial state, because of the single transaction. |

A conflict is retried only by re-deciding from fresh state. A failed `INSERT` is never retried blindly.

## 5. Why a VIN reservation table

"One IN_STOCK vehicle per VIN" spans aggregates. The options considered:

1. Deterministic aggregate ID from the VIN. This breaks re-stock after sale (A9).
2. Check the read model. It is eventually consistent, so it races.
3. **Reservation row written atomically with the events** (chosen). MySQL has no partial unique indexes, so a separate table keyed by VIN is the simplest strict implementation. `VehicleStocked` inserts the row and `VehicleSold` deletes it. It can be rebuilt from events if it is ever lost.

## 6. Read path & replay

- Load the full stream ordered by version. Streams are tiny (typically < 10 events), so **no snapshots** (02 §4).
- Replay asserts `version == previous + 1` and rejects unknown `(event_type, schema_version)`.
- `occurred_at` comes from the injected `Clock`, so tests are deterministic.
- A `ReadAll(afterPosition, limit)` method serves the projector's rebuild. A `ReadStream(aggregateID, fromVersion, toVersion)` method serves gap repair. Both are read-only.
